Kubernetes Deployment Strategies Explained

#kubernetes #devops #deployment #containers

Deploying to production shouldn't feel like defusing a bomb. Yet I've seen teams take down entire services because they didn't understand Kubernetes deployment strategies. Let me break down the three main approaches and when to use each.

Rolling Updates: The Default Choice

This is Kubernetes' default strategy, and it works great for most cases:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2        # Max pods above desired count
      maxUnavailable: 1  # Max pods that can be unavailable
  template:
    spec:
      containers:
      - name: myapp
        image: myapp:v2
        readinessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5

With these settings, Kubernetes will:

  • Create 2 new pods (maxSurge)
  • Wait for them to be ready
  • Terminate 1 old pod (maxUnavailable)
  • Repeat until all pods are updated

Pro tip: Always set readiness probes. Without them, Kubernetes will send traffic to pods that aren't ready, causing errors.

Blue-Green Deployments: Zero Downtime

Blue-green is perfect when you need instant rollback capability:

# Blue deployment (current)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-blue
spec:
  replicas: 10
  selector:
    matchLabels:
      app: myapp
      version: blue
  template:
    metadata:
      labels:
        app: myapp
        version: blue
    spec:
      containers:
      - name: myapp
        image: myapp:v1

---
# Green deployment (new)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-green
spec:
  replicas: 10
  selector:
    matchLabels:
      app: myapp
      version: green
  template:
    metadata:
      labels:
        app: myapp
        version: green
    spec:
      containers:
      - name: myapp
        image: myapp:v2

---
# Service (switch between blue and green)
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    app: myapp
    version: blue  # Change to 'green' to switch
  ports:
  - port: 80
    targetPort: 8080

To deploy:

# 1. Deploy green
kubectl apply -f myapp-green.yaml

# 2. Test green deployment
kubectl port-forward deployment/myapp-green 8080:8080

# 3. Switch traffic
kubectl patch service myapp -p '{"spec":{"selector":{"version":"green"}}}'

# 4. Rollback if needed (instant!)
kubectl patch service myapp -p '{"spec":{"selector":{"version":"blue"}}}'

The downside? You need 2x resources during deployment. But for critical services, it's worth it.

Canary Deployments: Test in Production Safely

Canary lets you test new versions with a small percentage of traffic:

# Stable deployment (90% traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-stable
spec:
  replicas: 9
  selector:
    matchLabels:
      app: myapp
      track: stable
  template:
    metadata:
      labels:
        app: myapp
        track: stable
    spec:
      containers:
      - name: myapp
        image: myapp:v1

---
# Canary deployment (10% traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-canary
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
      track: canary
  template:
    metadata:
      labels:
        app: myapp
        track: canary
    spec:
      containers:
      - name: myapp
        image: myapp:v2

---
# Service (routes to both)
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    app: myapp  # Matches both stable and canary
  ports:
  - port: 80
    targetPort: 8080

Monitor your canary metrics. If error rates spike, rollback immediately:

# Rollback: delete canary
kubectl delete deployment myapp-canary

# Promote: scale up canary, scale down stable
kubectl scale deployment myapp-canary --replicas=10
kubectl scale deployment myapp-stable --replicas=0

Which Strategy Should You Use?

Rolling Updates: Default choice for most applications. Simple, automatic, and works well.

Blue-Green: When you need instant rollback or zero downtime for critical services. Worth the extra resources.

Canary: When you want to test in production with minimal risk. Great for gradual rollouts.

Pro Tips

  • Always use readiness and liveness probes
  • Set appropriate resource limits
  • Use PodDisruptionBudgets to prevent too many pods going down
  • Monitor metrics during deployments
  • Have a rollback plan (and test it!)

The Deployment That Taught Me Everything

Last year, we deployed a new version using rolling updates. No readiness probe. The new pods started receiving traffic immediately, but they needed 30 seconds to warm up. Result? 30 seconds of 500 errors for every pod update. We took down the entire service.

Now? Every deployment has proper health checks, and we test rollbacks in staging. Learn from my mistakes.

Happy deploying! 🚀
