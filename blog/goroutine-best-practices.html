Goroutine Best Practices: Avoiding Common Pitfalls

#golang #concurrency #goroutines #backend

I'll be honest - goroutines are one of the reasons I fell in love with Go. They're lightweight, easy to use, and make concurrent programming feel almost too simple. But that simplicity can be deceiving. Over the past few years, I've debugged enough goroutine-related issues to write a book about what NOT to do.

So let me save you some pain and share the lessons I learned the hard way.

The Goroutine Leak That Cost Us $10K

Last year, our production API started eating memory like crazy. We were spinning up new instances every few hours just to keep things running. After days of debugging, we found the culprit - a goroutine leak in our notification service.

Here's what the code looked like (simplified):

func sendNotifications(users []User) {
    for _, user := range users {
        go func(u User) {
            // Send notification
            resp, err := http.Post(notificationURL, "application/json", body)
            if err != nil {
                log.Printf("failed to send: %v", err)
                return
            }
            defer resp.Body.Close()
        }(user)
    }
}

Looks innocent, right? The problem: we were creating goroutines without any way to track or limit them. When the notification service was slow or down, goroutines would pile up, each holding onto HTTP connections and memory.

Lesson #1: Never spawn goroutines without a way to control their lifecycle. Always use context for cancellation and worker pools for limiting concurrency.

The Right Way: Worker Pools

Here's how we fixed it:

func sendNotifications(ctx context.Context, users []User) error {
    const maxWorkers = 10
    jobs := make(chan User, len(users))
    results := make(chan error, len(users))
    
    // Start worker pool
    for w := 0; w < maxWorkers; w++ {
        go worker(ctx, jobs, results)
    }
    
    // Send jobs
    for _, user := range users {
        jobs <- user
    }
    close(jobs)
    
    // Collect results
    var errs []error
    for i := 0; i < len(users); i++ {
        if err := <-results; err != nil {
            errs = append(errs, err)
        }
    }
    
    return errors.Join(errs...)
}

func worker(ctx context.Context, jobs <-chan User, results chan<- error) {
    for user := range jobs {
        select {
        case <-ctx.Done():
            results <- ctx.Err()
            return
        default:
            results <- sendNotification(ctx, user)
        }
    }
}

This approach:

  • Limits concurrent goroutines to 10
  • Respects context cancellation
  • Properly handles errors
  • Cleans up resources

Channel Deadlocks: The Silent Killer

Here's another bug that haunted me for weeks. Can you spot the problem?

func processData(data []int) []int {
    results := make(chan int)
    
    for _, d := range data {
        go func(val int) {
            results <- val * 2
        }(d)
    }
    
    var processed []int
    for r := range results {
        processed = append(processed, r)
    }
    
    return processed
}

If you said "this will deadlock," you're absolutely right! The problem: we're ranging over results channel, but nobody ever closes it. The loop will wait forever.

Here's the fix:

func processData(data []int) []int {
    results := make(chan int, len(data))
    
    for _, d := range data {
        go func(val int) {
            results <- val * 2
        }(d)
    }
    
    // Close channel after all goroutines finish
    go func() {
        // Wait for all goroutines (you'd use sync.WaitGroup in real code)
        time.Sleep(time.Second)
        close(results)
    }()
    
    var processed []int
    for r := range results {
        processed = append(processed, r)
    }
    
    return processed
}

Better yet, use sync.WaitGroup:

func processData(data []int) []int {
    results := make(chan int, len(data))
    var wg sync.WaitGroup
    
    for _, d := range data {
        wg.Add(1)
        go func(val int) {
            defer wg.Done()
            results <- val * 2
        }(d)
    }
    
    // Close channel when all goroutines finish
    go func() {
        wg.Wait()
        close(results)
    }()
    
    var processed []int
    for r := range results {
        processed = append(processed, r)
    }
    
    return processed
}

Context: Your Best Friend

If there's one thing you take away from this post, let it be this: always use context for goroutines that do I/O or long-running operations.

Here's a real example from our codebase:

func fetchUserData(ctx context.Context, userID string) (*User, error) {
    // Create a channel for the result
    resultCh := make(chan *User, 1)
    errCh := make(chan error, 1)
    
    go func() {
        // Simulate slow database query
        user, err := db.GetUser(userID)
        if err != nil {
            errCh <- err
            return
        }
        resultCh <- user
    }()
    
    // Wait for result or context cancellation
    select {
    case user := <-resultCh:
        return user, nil
    case err := <-errCh:
        return nil, err
    case <-ctx.Done():
        return nil, ctx.Err()
    }
}

This pattern ensures that if the client cancels the request (or times out), we don't waste resources continuing the operation.

Common Mistakes I See All The Time

1. Forgetting to Pass Variables to Goroutines

// WRONG
for _, item := range items {
    go func() {
        process(item) // item is captured by reference!
    }()
}

// RIGHT
for _, item := range items {
    go func(i Item) {
        process(i)
    }(item)
}

2. Not Handling Panics

A panic in a goroutine will crash your entire program. Always recover:

go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("recovered from panic: %v", r)
        }
    }()
    
    // Your code here
}()

3. Ignoring Buffered Channels

Unbuffered channels can cause unnecessary blocking. If you know the size, use a buffered channel:

// Instead of this
results := make(chan Result)

// Do this
results := make(chan Result, expectedSize)

Testing Concurrent Code

Testing goroutines is tricky. Here's my approach:

func TestConcurrentProcessing(t *testing.T) {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    
    data := generateTestData(1000)
    results, err := processData(ctx, data)
    
    if err != nil {
        t.Fatalf("unexpected error: %v", err)
    }
    
    if len(results) != len(data) {
        t.Errorf("expected %d results, got %d", len(data), len(results))
    }
}

Always use timeouts in tests. If your code has a deadlock, you want to know immediately, not wait forever.

Tools That Saved My Life

1. Race Detector: Run your tests with go test -race. It's caught so many bugs for me.

2. pprof: Use runtime/pprof to profile goroutines:

import _ "net/http/pprof"

go func() {
    log.Println(http.ListenAndServe("localhost:6060", nil))
}()

// Then visit http://localhost:6060/debug/pprof/goroutine

3. Goleak: This library from Uber helps detect goroutine leaks in tests:

func TestMain(m *testing.M) {
    goleak.VerifyTestMain(m)
}

Final Thoughts

Goroutines are powerful, but with great power comes great responsibility (yeah, I went there). The key is to:

  • Always control goroutine lifecycle with context
  • Use worker pools to limit concurrency
  • Close channels when you're done
  • Handle panics gracefully
  • Test with race detector

I've made every mistake in this post (some multiple times). Learn from my pain, and may your goroutines never leak.

Stay concurrent, stay safe! 🔒
