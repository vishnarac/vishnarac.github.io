Infrastructure as Code with Terraform: Best Practices

#terraform #iac #devops #cloud

Managing infrastructure manually is like playing Russian roulette with your production environment. One wrong click and boom - your database is gone. Terraform changed how I think about infrastructure, and I'm never going back to clicking buttons in AWS console.

Why Terraform?

I've tried CloudFormation, Pulumi, and ARM templates. Terraform won because:

  • Works with multiple cloud providers
  • Declarative syntax that's actually readable
  • Massive community and module ecosystem
  • State management that actually works

Project Structure That Scales

Here's the structure I use for all projects:

terraform/
├── environments/
│   ├── dev/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   ├── staging/
│   └── prod/
├── modules/
│   ├── vpc/
│   ├── eks/
│   └── rds/
└── global/
    └── s3-backend/

Never put everything in one file. Your future self will thank you.

State Management

Always use remote state. Always. Here's my S3 backend setup:

terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}

The DynamoDB table prevents concurrent modifications. I learned this after two engineers applied changes simultaneously and corrupted the state. Not fun.

Writing Reusable Modules

Modules are your best friend. Here's a simple VPC module:

# modules/vpc/main.tf
resource "aws_vpc" "main" {
  cidr_block           = var.cidr_block
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = merge(
    var.tags,
    {
      Name = "${var.environment}-vpc"
    }
  )
}

resource "aws_subnet" "public" {
  count             = length(var.public_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.public_subnet_cidrs[count.index]
  availability_zone = var.availability_zones[count.index]

  tags = merge(
    var.tags,
    {
      Name = "${var.environment}-public-${count.index + 1}"
      Type = "public"
    }
  )
}

# modules/vpc/variables.tf
variable "environment" {
  description = "Environment name"
  type        = string
}

variable "cidr_block" {
  description = "VPC CIDR block"
  type        = string
}

variable "public_subnet_cidrs" {
  description = "Public subnet CIDR blocks"
  type        = list(string)
}

variable "availability_zones" {
  description = "Availability zones"
  type        = list(string)
}

variable "tags" {
  description = "Common tags"
  type        = map(string)
  default     = {}
}

Now you can reuse this across environments:

module "vpc" {
  source = "../../modules/vpc"

  environment          = "prod"
  cidr_block          = "10.0.0.0/16"
  public_subnet_cidrs = ["10.0.1.0/24", "10.0.2.0/24"]
  availability_zones  = ["us-east-1a", "us-east-1b"]

  tags = {
    Project = "MyApp"
    Team    = "Platform"
  }
}

Variable Management

Use terraform.tfvars for environment-specific values:

# environments/prod/terraform.tfvars
environment = "prod"
instance_type = "t3.large"
min_size = 3
max_size = 10
db_instance_class = "db.r5.xlarge"

Never commit secrets! Use environment variables or AWS Secrets Manager:

# Use environment variables
export TF_VAR_db_password="super-secret"

# Or reference from Secrets Manager
data "aws_secretsmanager_secret_version" "db_password" {
  secret_id = "prod/db/password"
}

resource "aws_db_instance" "main" {
  password = data.aws_secretsmanager_secret_version.db_password.secret_string
}

Workspaces for Multiple Environments

Workspaces are great for managing multiple environments:

# Create workspaces
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod

# Switch between them
terraform workspace select prod

# Use workspace name in resources
resource "aws_instance" "app" {
  tags = {
    Environment = terraform.workspace
  }
}

Data Sources for Existing Resources

Don't recreate what already exists:

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-focal-20.04-amd64-server-*"]
  }
}

data "aws_vpc" "existing" {
  tags = {
    Name = "legacy-vpc"
  }
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.ubuntu.id
  subnet_id     = data.aws_vpc.existing.id
}

Conditional Resources

Use count for conditional creation:

resource "aws_instance" "bastion" {
  count = var.create_bastion ? 1 : 0
  
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
}

# Reference with index
output "bastion_ip" {
  value = var.create_bastion ? aws_instance.bastion[0].public_ip : null
}

Lifecycle Rules

Prevent accidental deletions:

resource "aws_db_instance" "prod" {
  lifecycle {
    prevent_destroy = true
    
    ignore_changes = [
      password,  # Don't update if password changes
    ]
    
    create_before_destroy = true
  }
}

My Terraform Workflow

# 1. Format code
terraform fmt -recursive

# 2. Validate syntax
terraform validate

# 3. Plan changes
terraform plan -out=tfplan

# 4. Review the plan carefully
# 5. Apply if everything looks good
terraform apply tfplan

# 6. Commit state lock
git add .
git commit -m "Applied infrastructure changes"

Common Mistakes to Avoid

1. Not using remote state: Local state files will bite you eventually.

2. Hardcoding values: Use variables for everything that might change.

3. Not using modules: Copy-pasting code is a recipe for inconsistency.

4. Ignoring state locking: Concurrent applies will corrupt your state.

5. Not reviewing plans: Always check what Terraform will do before applying.

Pro Tips

  • Use terraform graph | dot -Tpng > graph.png to visualize dependencies
  • Enable debug logging: export TF_LOG=DEBUG
  • Use terraform state list to see all resources
  • Import existing resources: terraform import aws_instance.example i-1234567890abcdef0
  • Use terraform taint to force resource recreation

Final Thoughts

Terraform isn't perfect, but it's the best tool we have for infrastructure as code. Start small, use modules, and always review your plans. Your infrastructure will be more reliable, reproducible, and maintainable.

And remember: with great power comes great responsibility. One wrong terraform destroy and you're having a very bad day.

Happy terraforming! 🏗️
